# Сайт-портфолио Павла Михайлова — дизайн-документ

Дата: 2026-07-27
Статус: утверждён

## 1. Задача

Портфолио Павла Михайлова (Senior Product Designer) сейчас живёт в Yonote как шаренный wiki-документ. Как витрина для рекрутеров это не работает:

- нет собственного адреса и брендинга;
- при отправке ссылки в мессенджер не появляется превью;
- страница грузится как SPA — сначала виден экран «Загрузка…»;
- вёрстка под чтение вики, а не под просмотр кейсов с телефона;
- изображения отдаются через временные ссылки `attachments.redirect`, которые могут перестать работать.

Делаем самостоятельный статический сайт на GitHub Pages. После импорта Yonote перестаёт быть зависимостью: весь контент и все изображения лежат в репозитории.

**Успех:** рекрутер открывает ссылку с телефона, за секунду видит кто это и с какими результатами, за два клика попадает в нужный кейс и может отправить ссылку на конкретный кейс коллеге — с превью.

## 2. Границы

**В объёме:** лендинг, 6 страниц кейсов, тёмная тема, адаптив, SEO и OG-превью, деплой на GitHub Pages.

**Вне объёма:** формы обратной связи, аналитика, CMS, английская версия, блог, анимации сверх переходов состояний. Английская версия и свой домен — вероятные кандидаты на следующую итерацию, архитектура не должна им мешать (тексты вынесены в контент-файлы, домен меняется одной строкой конфига).

## 3. Технические решения

| Решение | Выбор | Причина |
|---|---|---|
| Фреймворк | Astro 5 + React islands | статика по умолчанию, JS только там, где нужен |
| Стили | Tailwind CSS 4 + shadcn/ui | конфиг в CSS, примитивы копируются в репозиторий |
| Шрифт | Inter, self-hosted | без обращений к CDN — важно для скорости в РФ |
| Хостинг | GitHub Pages, project page | `https://nkonovalov1990.github.io/Pavelmkh/`, `base: '/Pavelmkh'` |
| Язык | только русский | контент уже на русском |
| Контент | разовый импорт в репозиторий | нет хрупкой зависимости от Yonote в рантайме |
| Тесты | Vitest + Playwright + axe | unit для логики, e2e для того, ради чего сайт существует |

### 4.3 Импорт

`POST /api/documents.info` с `shareId` работает без авторизации, но отдаёт плоский текст без заголовков, списков и изображений. Поэтому импорт — парсинг DOM через Playwright, а не через API.

`scripts/import-yonote.mjs`, запускается один раз:

1. открывает каждый из 6 URL, ждёт `.ProseMirror`;
2. сериализует DOM → Markdown через `turndown`;
3. скачивает изображения в `src/assets/cases/<slug>/NN.<ext>`, подменяет `src`;
4. скачивает CV в `public/Pavel_Mikhaylov_CV.pdf`;
5. пишет `src/content/cases/<slug>.mdx` со скелетом frontmatter.

`summary`, `metrics` и `alt` у изображений дописываются вручную — машинно их не получить. Результат коммитится; дальше контент правится в репозитории.

Тексты переносятся как есть. Правится только форматирование: эмодзи-маркеры ❌/✅ становятся подписями к изображениям, убираются неразрывные пробелы и пустые абзацы.

  components/*.astro      Header, Hero, CaseCard, CaseGrid, Contacts, Footer, BaseHead

### 5.1 Схема кейса

```ts
z.object({
  title: z.string(),
  company: z.string(),
  order: z.number(),
  summary: z.string().max(200),
  role: z.array(z.string()).min(1),
  outcome: z.string(),
  metrics: z.array(z.object({ value: z.string(), label: z.string() })).default([]),
  cover: image(),
  year: z.number().optional(),
  draft: z.boolean().default(false),
})
```

Схема экспортируется отдельно от `content.config.ts`, чтобы её можно было юнит-тестировать без запуска Astro.

### 5.2 Границы модулей

- `lib/site.ts` — данные профиля. Не знает про компоненты.
- `content/` — данные кейсов. Не знают про вёрстку.
- `components/*.astro` — вёрстка. Получают данные пропсами, не читают коллекции сами; исключение — страницы в `pages/`, которые и являются точкой сборки данных.
- `components/react/*` — только интерактив. Каждый остров работает без знания о соседях.
- `lib/utils.ts` — `withBase()` единственная точка, знающая про base path.

### 5.3 Тёмная тема

Инлайновый скрипт в `<head>` до первой отрисовки читает `localStorage.theme`, при отсутствии — `prefers-color-scheme`, ставит класс `dark` на `<html>`. `ThemeToggle` грузится с `client:load` — это единственный остров с немедленной загрузкой; `Lightbox` — с `client:visible`.

Гамбургер-меню на мобильном не делаем: в шапке три элемента, они помещаются на 390 px. Это убирает `Sheet` и один React-остров.

Скриншоты макетов в кейсах светлые, поэтому в тёмной теме получают нейтральную подложку и рамку.

### 5.4 Обработка ошибок

Статический сайт, рантайм-ошибок почти нет. Значимые отказы ловятся на сборке:

- невалидный frontmatter → сборка падает с указанием файла (Zod);
- отсутствующее изображение → сборка падает (astro:assets);
- битая внутренняя ссылка → ловится e2e-тестом навигации;
- неизвестный URL у пользователя → страница 404 со ссылкой на главную.

## 6. Критерии приёмки

Каждый тест ссылается на свой AC в заголовке: `test('AC-7: ...')`.

### Контент

- **AC-1.** Все 6 MDX-файлов проходят валидацию схемы; невалидный frontmatter роняет сборку.
- **AC-2.** В `dist/` нет ни одного упоминания `pavelmikhaylov93.yonote.ru` — сайт автономен.
- **AC-3.** Каждый кейс имеет непустые `title`, `company`, `summary`, `role`, `outcome`, `cover`.
- **AC-4.** У всех содержательных `<img>` в собранном сайте непустой `alt`. Исключение — изображение внутри ссылки, рядом с которой тот же смысл уже передан текстом: такая картинка декоративна и обязана нести `alt=""`, иначе скринридер озвучит одно и то же дважды. Единственный такой случай — обложка в карточке кейса, где в ссылке уже есть компания и заголовок.

  Исходно критерий требовал непустой `alt` вообще у всех изображений. Это было слишком грубо: правило «alt должен быть везде» на практике вредит доступности ровно в этом случае.

### Главная

- **AC-5.** Главная содержит имя, роль и текст био.
- **AC-5a.** В герое есть портрет Павла с осмысленным `alt`, отданный в современных форматах и с `srcset` под разные плотности экрана.
- **AC-6.** Главная показывает ровно 6 карточек кейсов, отсортированных по `order`.
- **AC-7.** Клик по карточке ведёт на `/Pavelmkh/case/<slug>/`.
- **AC-8.** Три внешних контакта ведут на верные URL и имеют `target="_blank"` и `rel="noopener"`.
- **AC-9.** Ссылка на CV отдаёт HTTP 200 и `content-type: application/pdf`.

### Страница кейса

- **AC-10.** Каждая страница кейса содержит `h1` с названием, компанию, роль и результат.
- **AC-11.** Изображения кейса открываются в лайтбоксе; лайтбокс закрывается по Esc и по клику вне, фокус возвращается на триггер.
- **AC-12.** На странице кейса есть переход к следующему и предыдущему кейсу и возврат на главную.

### Адаптив

- **AC-13.** На 390×844 нет горизонтального скролла ни на одной странице.
- **AC-14.** На 390×844 сетка кейсов в одну колонку; на 1440×900 — в две или три.
- **AC-15.** На 390×844 вся навигация шапки видна и кликабельна без гамбургер-меню, целевые области не меньше 44×44 px.

### Тема

- **AC-16.** Переключение темы сохраняется после перезагрузки.
- **AC-17.** При первом визите тема берётся из `prefers-color-scheme`.
- **AC-18.** Класс `dark` выставлен на `<html>` до события `load` — вспышки светлой темы нет.

### SEO

- **AC-19.** У каждой страницы уникальные `title` и `meta description`.
- **AC-20.** У каждой страницы есть `og:title`, `og:description`, `og:image` и `canonical` с полным абсолютным URL.
- **AC-21.** Собраны `sitemap-index.xml` и `robots.txt`, в карте присутствуют все 7 страниц.
- **AC-22.** Неизвестный URL отдаёт страницу 404 со ссылкой на главную.

### Доступность

- **AC-23.** axe не находит нарушений serious и critical на главной и на каждой странице кейса, в светлой и тёмной теме.
- **AC-24.** Навигация с клавиатуры доходит до всех интерактивных элементов, фокус виден.
- **AC-25.** Контраст текста не ниже 4.5:1 в обеих темах.

### Производительность и сборка

- **AC-26.** Суммарный вес JS, реально подключаемого страницами сайта, меньше 120 KB в gzip.

  Исходно здесь стояло «100 KB», но это число было назначено без учёта того, что shadcn/ui — React-библиотека: один только рантайм React 19 весит ~195 KB сырых и ~61 KB в gzip. Бюджет измеряется в gzip, потому что именно столько скачивает пользователь, и считает только те файлы, на которые есть ссылка в собранном HTML: Astro кладёт в `dist/` клиентский рантайм даже когда островов на странице нет, и неподключённый файл трафика не создаёт. При ожидаемой начинке (React ~61 KB, Radix Dialog и иконки ~20 KB, свой код ~5 KB) порог в 120 KB оставляет запас, но ловит удвоение.
- **AC-27.** Все внутренние ссылки и ассеты содержат префикс `/Pavelmkh` — на project page ничего не ломается.
- **AC-28.** `npm run build` завершается без ошибок и предупреждений Astro.
- **AC-29.** CI гоняет unit и e2e на каждый PR; деплой на Pages идёт только с `main` и только при зелёных тестах.

## 7. Стратегия тестирования

**Vitest (jsdom)** — схема контента и валидация всех 6 MDX через `gray-matter`; `withBase()`; `ThemeToggle` и `Lightbox` через Testing Library; `CaseCard` через `experimental_AstroContainer`.

**Playwright** — прогон против `astro build && astro preview` с настоящим base, а не с `/`. Покрывает AC-5…AC-22, AC-26, AC-27.

**axe** — `@axe-core/playwright`, AC-23…AC-25.

Порядок работы строго red → green → refactor: сначала падающий тест со ссылкой на AC, потом минимальная реализация.
